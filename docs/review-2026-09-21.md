## F1 — `centre_distance` returns confidently wrong numbers

**Severity: high (silent incorrect output).**  `calc.py:181`

The Newton iteration solves `inv(aw) = target` where

```
target = inv(α) + 2·tan(α)·Σx / (z₁ + z₂)
```

`inv(a) = tan(a) − a` is non-negative on `(0, π/2)`, so when `target ≤ 0` **no working
pressure angle exists** — the pair cannot mesh at any centre distance. The loop has no
convergence test and no domain check; it wanders for its fixed 40 iterations and returns
whatever it lands on.

Checked against a bisection reference over the whole feasible parameter grid: **138
parameter sets return garbage**, all of them in the `target ≤ 0` region, all `200 OK`
with no warning.

```
GET /api/info?teeth=6&pressure_angle=14.5&profile_shift=-0.6&mate_teeth=40
   → centre_distance = 39.428     nominal 70.0     (−44 %)
GET /api/info?teeth=6&pressure_angle=14.5&profile_shift=-0.5&mate_teeth=12
   → centre_distance = 59.674     nominal 21.0     (3×)
```

Some inputs return a **negative** centre distance. Outside the `target ≤ 0` region the
iteration matched bisection to 1e-6 everywhere, so the formula is right and only the
solver and its domain are wrong.

This is the tool's headline "match a real gear" number; a wrong value here gets cut into
a bracket.

## F2 — Caches are bounded by entry count, not by bytes

**Severity: high (unbounded memory / OOM).**  `model.py:168`, `model.py:184`

Two `lru_cache(maxsize=32)` hold whole OpenCascade solids and whole export blobs.
Anonymous RSS measured inside the container (`/sys/fs/cgroup/memory.stat`):

| Workload | anon RSS |
|---|---|
| fresh container | 196 MiB |
| 40 distinct default-size gears, preview quality | 300 MiB |
| **5** large fine gears (190–198 teeth) | **1 591 MiB** (~280 MiB each) |
| 35 large gears | **~3.0 GiB**, never released, file cache evicted |

`compose.yaml` sets `SPUR_WORKERS: "2"`, and the caches are per process, so the worst
case is ~6 GiB with no `mem_limit` anywhere. On the Raspberry Pi 5 the README advertises
this OOMs, and `restart: unless-stopped` turns that into a restart loop.

Normal UI use is fine; the cost scales with part size, and `maxsize` is a count.

## F3 — Bore/recess defaults are absolute mm and do not scale with the gear

**Severity: high (first thing a new user hits).**  `params.py:53-75`, `calc.py:114-119`

The README's own CLI example does not run:

```
$ spur export -o gear.stl --teeth 24 --module 1 --pressure-angle 20 --bore-flat 0
error: Recess cuts into the bore wall; reduce its width or inner Ø.
       Recess cuts into the tooth rim; reduce its width or inner Ø.       exit=2
```

Same parameters over the API → 422. The cause is design, not a typo: `bore_d = 9` and
`recess_width = 6` are absolute millimetres tuned for the 19-tooth m=1.75 gear (root Ø
28.9 mm). At m=1, z=24 the root Ø is 21.5 mm and they no longer fit, so the user gets a
wall of errors about two parameters they never touched.

Across the standard grid (module 0.5–3.0, teeth 6–120), **17 % of combinations are
infeasible at stock defaults**, and it is the small-gear corner where people start:

```
m=0.5  needs z≥52      m=1.0  needs z≥28      m=1.75 needs z≥18      m=3.0  needs z≥12
m=0.6  needs z≥44      m=1.25 needs z≥22      m=2.0  needs z≥16
m=0.8  needs z≥34      m=1.5  needs z≥20      m=2.5  needs z≥14
```

## F4 — No admission control; a build stalls the event loop

**Severity: medium (availability under trivial load).**  `model.py:29`, `app.py:85`

OpenCascade work holds the GIL, and the builds all serialize on `_LOCK` anyway, so
queued threads buy nothing but latency. Measured `/api/health` latency:

- **one** 200-tooth fine build in flight: `0.22 s → 0.76 s → 2.00 s`, then recovers.
- **ten** concurrent builds: health repeatedly exceeded 5 s and timed out.

The Docker `HEALTHCHECK` is `--timeout=5s --retries=3`, so modest concurrency marks the
container unhealthy — on a 12-core machine. A Pi 5 is far worse.

Related: aborting in the browser does not cancel server work (`app.js:174`), so dragging
a slider queues builds nobody will read.

## F5 — `requirements.txt` pins 6 of 56 installed packages

**Severity: medium (reproducibility).**  `requirements.txt:1`

The header says "tested together", but only the six direct dependencies are pinned.
`pip freeze` in the built image shows 50 transitive packages resolved at build time —
`numpy==2.5.3`, `starlette==1.6.0`, `scipy`, `numba`, `llvmlite`, `matplotlib`,
`casadi`, `trame`, … A rebuild next month produces a different image, and a `starlette`
major release breaks the build with no warning.

## F6 — `root_thickness` is measured at the wrong radius

**Severity: low (wrong displayed number).**  `calc.py:69`

`_tooth()` computes the gap at `rf` but the thickness at `r_start`. When `rb > rf` —
which is the case for **the project's own default gear** — the two disagree:

```
z=19: reported root_thickness 3.3040 + root_gap 1.6085 = 4.9125
      root-circle pitch                                  4.7744    (+2.9 %)
      true tooth thickness at root Ø 28.875              3.1659
```

The UI labels it "Tooth at root" and shows 3.304 mm. For z ≳ 27 (where `rf > rb`) it is
exact, which is why no test caught it.

## F7 — ~440 MB of the image is never imported

**Severity: low (image size).**  `Dockerfile:20`

Measured, not guessed. Uninstalling `trame*`, `wslink`, `matplotlib`, `scipy`, `numba`,
`llvmlite`, `pillow`, `fontTools`, `aiohttp` and friends takes site-packages from
**1 767 MB → 1 325 MB** and STL + STEP export still works.

`vtk` (639 MB) is **not** removable — `OCP` links `libvtkWrappingPythonCore`. `casadi`,
`nlopt`, `ezdxf` and `pyparsing` are imported eagerly by `cadquery`. Verified by
uninstalling and re-adding until `export()` worked again.

The README also says the image is "about 1.5 GB". It is 2.15 GB (amd64) / 2.07 GB (arm64).

## F8 — Structure and process notes

**Severity: low.**

- `model.py:113` `_build()` mixes altitudes: product decisions (which faces get a recess,
  what a D-flat means) sit inline with kernel mechanics — `geomType() == "CIRCLE"`,
  `1e-6` literals, the `on_bore_rim` positional predicate. The edge-selection predicates
  are the design secret worth hiding; the rest already reads clearly.
- `model.py:123` `floors` is a list of two z-values, one the cut origin and one the floor.
  Correct, but the reader has to derive that.
- `app.py:53` `_gear()` re-runs the full `check()` on every request, and the reason it
  exists (normalising the cache key away from the `InfoQuery`/`ModelQuery` subclass) is
  not written down.
- `cli.py` is 111 lines with **zero tests**. A smoke test of the README's own commands
  would have caught F3.
- **No CI.** Nothing runs `pytest`, builds the image, or checks that the vendored bundle
  still matches `web/` — the last of which passed here, and is exactly the kind of
  property that rots silently.
- Sub-path deployment: under `SPUR_ROOT_PATH=/spur` a proxied `GET /spur` (no trailing
  slash) returns 200, and the browser then resolves `static/style.css` to `/static/…`.
  The proxy must redirect to `/spur/`; this is undocumented.
