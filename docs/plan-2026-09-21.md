# Remediation plan — review of 2026-09-21

Findings: [`review-2026-09-21.md`](review-2026-09-21.md). Ordered by severity, grouped so
each step is independently testable and independently revertable.

## Decisions taken before starting

- **F3 is fixed by capping, not by rescaling the defaults.** The annular face recess is a
  weight-saving feature, so when it does not fit between the bore wall and the tooth rim
  it is narrowed to fit and a warning is emitted — the same "cap and warn" contract
  `root_fillet()` already uses. Rescaling the default *values* was rejected: every
  existing shareable link that omits a field would silently build a different gear.
- **Only the recess width is capped.** `recess_depth` vs `face_width` stays a hard error:
  that is a direct conflict between two dimensions the user set explicitly, and the fix
  is unambiguous. A too-large `bore_d` also stays an error — silently shrinking someone's
  shaft bore is worse than refusing.
- **No currently-valid gear may change shape.** Verified numerically for the defaults
  before and after (`recess_id` stays 13.013 mm).
- **Admission control lives in `app.py`, not `model.py`.** Queue depth is a web-serving
  policy; the CLI must not inherit a queue.

## Step 1 — F1: `centre_distance` domain and solver

- `calc.py`: compute `target` explicitly; return `None` when `target <= 0` (no working
  pressure angle exists, so the pair cannot mesh at any centre distance).
- Replace the unguarded 40-step Newton with bisection on `(0, 89°)`. `inv` is monotonic
  there; 60 iterations reach full double precision and the function has no failure mode.
- Add `mate_report()` so the "no solution → warn instead of report" decision is written
  once and shared by the API and the CLI. This also fixes the CLI omitting `mate_teeth`
  from its JSON, which the API includes.
- Tests: the two reproductions from F1, a bisection cross-check over the feasible grid,
  and the existing unshifted/shifted expectations.

## Step 2 — F6: `root_thickness` radius

- `calc.py:_tooth()`: measure the thickness at `rf`, like the gap already is.
- Test: `root_thickness + root_gap == 2π·rf/z` for both `rb > rf` (z=19) and `rf > rb`
  (z=40). The second case is the regression guard — it passes today.

## Step 3 — F3: cap the recess instead of refusing

- `calc.py:recess_radii()` returns the recess narrowed into the annulus
  `[bore_radius + bore_chamfer + MIN_WALL, rf - MIN_WALL]`, or `None` when that annulus
  is narrower than `MIN_RECESS_WIDTH`. The existing centring rule is kept verbatim and
  only clamped, so the default gear is unchanged.
- Add `recess_fillet()` mirroring `root_fillet()`, capped to the *effective* width.
- `check()` loses three errors (recess into bore wall, recess into rim, recess fillet too
  large); `derive()` gains the corresponding warnings. `model.py` consumes the effective
  fillet rather than the requested one.
- Tests: the README example now builds; defaults produce no warnings and identical
  dimensions; the dropped errors are replaced by warning assertions.

## Step 4 — F2: bound the caches by bytes

- Replace `lru_cache` on the export blobs with a small LRU bounded by total bytes
  (`SPUR_EXPORT_CACHE_MB`, default 64).
- Drop the solid cache from 32 entries to `SPUR_SOLID_CACHE` (default 4) — the solids,
  not the blobs, are what cost ~280 MiB each.
- `compose.yaml`: add a memory limit as the backstop the cache tuning cannot provide.
- Re-measure anon RSS with the same workload as F2 and record the numbers.

## Step 5 — F4: admission control

- `app.py`: a bounded, non-blocking queue slot around model requests
  (`SPUR_MAX_QUEUED_BUILDS`, default 4); return `503` + `Retry-After` when saturated
  rather than piling up work that serialises on the kernel lock anyway.
- Raise the Docker `HEALTHCHECK` timeout to 10 s: one large build legitimately stalls
  the event loop for ~3 s, and failing liveness for that is wrong.
- Honest limitation to document: this bounds the queue, it does not stop a single large
  build from blocking the loop. That needs a process pool, which is out of scope here.

## Step 6 — F5 + F7: reproducible and smaller image

- Regenerate `requirements.txt` as a full pinned freeze of the resolved set.
  `pyproject.toml` keeps its loose ranges.
- `Dockerfile`: uninstall the verified-unused transitives in the same layer, and upgrade
  the build-time smoke test from `import spur.model` to a real `export()` so a future
  `cadquery` that starts importing `scipy` fails the build, not production.
- Verify by building **both** architectures from the lock.

## Step 7 — F8: structure, docs, CI

- `model.py`: split `_build()` into intent-named steps; name the recess floor tuple.
- `app.py`: one comment on why `_gear()` exists.
- README: correct the image size, fix the broken CLI example, document the new env vars
  and the sub-path trailing-slash requirement.
- Add CLI tests (the README's own commands) and a minimal CI workflow: `pytest`, a
  docker build, and a check that the vendored three.js bundle still matches `web/`.

## Out of scope, recorded deliberately

- Moving CAD work to a process pool to stop event-loop stalls (F4's root cause).
- Cancelling server-side work when the browser aborts (`app.js:174`).
- Trochoidal root fillets for undercut gears — already documented as a known
  approximation in the README's geometry notes.

# Outcome

All seven steps landed. Measured before/after, same machine, native arm64 unless noted.

| | Before | After |
|---|---|---|
| F1 impossible pairs returning a number (15 660-case grid) | 138 | **0** |
| F1 values disagreeing with an independent bisection solver | — | **0** |
| F2 anon RSS after 40 distinct 160–199 tooth fine gears | ~3.0 GiB, still climbing | **358 MiB, flat from gear 10** |
| F2 anon RSS, normal UI session (40 default-size previews) | 300 MiB | 286 MiB |
| F3 feasible share of the (module 0.5–3, teeth 6–120) grid | 83 % | **94 %** |
| F3 README's own CLI example | `exit=2` | runs, warns that the recess was narrowed |
| F4 health probe timeouts under 10 concurrent builds | 3 of 25 | **0 of 20** (slowest 4.9 s, limit now 10 s) |
| F4 behaviour past the queue depth | unbounded pile-up | `503` + `Retry-After` (6 of 10 refused) |
| F5 packages pinned | 6 of 56 | **31 of 31** |
| F6 `root_thickness + root_gap` vs root-circle pitch, z=19 | 4.9125 vs 4.7744 | **4.7744 vs 4.7744** |
| F7 image, amd64 / arm64 | 2.15 GB / 2.07 GB | **1.70 GB / 1.61 GB** |
| Tests | 34 | **50** |

Two results worth calling out because they contradict the plan's own reasoning:

- **Cache sizing was the wrong lever for F2.** Trimming the caches moved the plateau from
  1.87 GiB to 1.5 GiB and no further: almost all of it was glibc holding freed arenas
  after OpenCascade's allocation churn, not live cached data. A `malloc_trim(0)` after
  each cache-missing export took it to 358 MiB. The bounded caches stay — they are what
  makes the ceiling predictable — but the arena release is what did the work.
- **`mem_limit: 1g` was too tight** and failed ~5 % of requests under the sweep even
  though steady state is ~740 MB for two workers: a single large build peaks well above
  its resting size. The compose file says 2 g, measured.

## Deliberately not done

- Moving CAD work to a process pool. It is the root cause of F4 — one build still stalls
  the event loop for a few seconds because OpenCascade holds the GIL — and the
  healthcheck timeout now accommodates that rather than fixing it.
- Cancelling server-side work when the browser aborts (`app.js:174`).
- `.github/workflows/ci.yml` is **unverified**: GitHub Actions cannot be run here. The
  YAML parses and each step mirrors a command that was run by hand during this work,
  but the workflow itself has never executed.
