# Как разрабатывать spur (гид для человека)

Цикл, по которому идёт работа с AI-агентами в этом репозитории, и твоя роль на каждом
шаге.

```
обсуждение -> план -> проверка плана -> выполнение (ветка фазы) -> приёмка -> PR -> ревью другим CLI -> merge
  ты ставишь   AI пишет    ты одобряешь      AI строит на gsd/phase-NN    ты проверяешь  CI   кросс-проверка    squash
     цель        план
```

Один проход = одна фаза = одна ветка = один PR = один squash-коммит в `main`. Держи
фазы маленькими.

## 0. Что уже гарантировано

Прежде чем говорить про цикл — вот что в репозитории стоит и работает, чтобы сырое не
проскочило:

- `make verify` — единый гейт: ruff, mypy `--strict`, контракты границ импортов, скан
  незавершёнки (`TODO`/`FIXME`/`NotImplementedError`), pytest. ~11 с на прогретом кеше.
- Тот же `make verify` стоит в pre-commit хуке, в CI (на каждый push в `main` и на
  каждый PR, Python 3.10 и 3.12) и внутри `make worktree.land` перед вливанием. Одно
  определение «прошло» в трёх местах.
- `gsd-ship` не создаст PR, пока верификация фазы не `passed`, дерево не чистое, а
  `SECURITY.md` фазы не утверждает `threats_open: 0`. Шлюз, а не напоминание.
- `make check` — всё то же плюс сборка образа, smoke-тест внутри контейнера и проверка,
  что вендоренный three.js байт в байт собирается из `web/`. Нужен Docker.
- `AGENTS.md` — правила, которые агент читает первым делом; `docs/architecture/` — карта
  системы и журнал решений `Lxx`.

Первый прогон после `make clean` подтягивает ~1.4 ГБ OpenCascade и занимает пару минут —
это страничный кеш, а не тесты.

## 1. Обсуждение

`gsd-discuss-phase` (для первой настройки проекта в gsd — `gsd-map-codebase`, затем
`gsd-ingest-docs`). Обсуди, что нужно дальше. Твоя роль: сформулировать цель и
ограничения, а не решение.

## 2. План

`gsd-plan-phase`. Агент пишет пошаговый план в `.planning/`. Твоя роль: дождаться.

Коммиты плана ложатся в `main`. **После плана — `git push origin main`**: ветка фазы на
шаге 4 режется от `origin/main`, а не от локального HEAD, и незапушенный план в неё
просто не попадёт. Правило простое: `main` всегда запушен до `gsd-execute-phase`.

## 3. Проверка и правка плана

`gsd-review --phase N` — второй CLI смотрит план до того, как что-то написано.

**Не одобряй план, который не понимаешь — спрашивай, пока не поймёшь.** Здесь ошибка
стоит минут, после сборки — часов.

Для этого проекта на плане особенно стоит проверить три вещи:

- Меняется ли форма детали, которую пользователь не просил менять? Дефолты заморожены
  (`L05`), каждая ссылка на модель опирается на них.
- Появляется ли число, которое может быть неправдой? Правило `L08`: лучше предупреждение
  без числа, чем правдоподобное число.
- Есть ли измерение под утверждением о скорости или памяти? В этом репозитории так
  принято: в комментариях стоят цифры и нагрузка, на которой они получены.

## 4. Выполнение на ветке фазы

`gsd-execute-phase N`. В `.planning/config.json` стоит `git.branching_strategy: "phase"`,
поэтому команда сама режет ветку `gsd/phase-NN-<slug>` от `origin/main`, переключает на
неё основной checkout и складывает туда все коммиты фазы — планы, код, верификацию,
`ROADMAP`/`STATE`. `main` остаётся тем, что уже влито. По ходу работы `make verify`
должен оставаться зелёным.

Внутри фазы gsd может гонять исполнителей параллельных планов в агентских worktree
(`.claude/worktrees/agent-*`). На ветке фазы это почти никогда не срабатывает: Claude Code
режет такие worktree от `origin/HEAD`, и как только на ветке появился первый коммит, gsd
честно откатывается на последовательное выполнение в основном checkout'е и пишет об этом
`⚠ Worktree base mismatch`. Это норма, не поломка — фаза 2 прошла так целиком.

**Одна ловушка, специфичная для этого проекта.** У любого worktree — и агентского, и
сделанного руками через `make worktree.new` — нет своего `.venv`, а он здесь весит
~1.4 ГБ. Соблазн — подсунуть общий из основного checkout'а. Так делать нельзя, и это
проверено: editable-установка в `.venv` прописана на `src/` основного checkout'а, поэтому
`import spur` из worktree резолвится обратно туда, и тесты молча проверяют неизменённый
код и проходят. Либо `make venv` внутри worktree (первый `make verify` там сделает это
сам — пара минут), либо `make test-image` (гоняет суиту в контейнере, локальный Python не
нужен). Команда `make worktree.new` печатает это напоминание сама.

## 5. Приёмка

`gsd-verify-work N` — на ветке фазы, до PR. Пройди фичу как пользователь. Для spur это
значит: открыть UI, собрать деталь, посмотреть на предупреждения и — если менялась
геометрия или числа — сверить измерения. Не сошлось — назад к обсуждению, а не вслепую
патчить.

Почему до PR: `gsd-ship` откажется от фазы, чья верификация не `passed`, а именно твои
ручные проверки переводят её из `human_needed` в `passed`. Туда же, до PR:
`gsd-secure-phase N` (даёт `SECURITY.md`, без него ship не пройдёт) и
`gsd-validate-phase N`.

## 6. PR

```sh
/gsd-ship N
```

Проверяет верификацию, чистое дерево и что ты не на `main`; пушит ветку фазы; создаёт PR
«Phase N: …» в `main` с телом, собранным из артефактов планирования. CI запускается на
PR сам — зелёный CI до merge, а не после.

Коммит ship-note несёт `[ci skip]` в теме, и `no-skip-token`-хук (D-02) его отказывает:
`gsd-ship` печатает предупреждение и оставляет `.planning/STATE.md` изменённым, но
незакоммиченным. Закоммить руками: `docs(NN): ship phase N — PR #M`, без токена, и
`git push`. Пуш запускает ещё один прогон CI (~3 мин) на новом HEAD PR — именно его
требует `make pr.land`. Глобальный `~/.claude/gsd-core/workflows/ship.md` не патчится:
правка потеряется при следующем обновлении gsd и невидима этому репозиторию.

## 7. Ревью кода *другим* CLI

Писал Claude → ревьюит **Codex**; писал Codex → ревьюит **Claude**. Обе CLI читают один и
тот же `AGENTS.md`, так что правила у них общие, а взгляд разный. Вторая модель не станет
штамповать одобрение собственной работе. Предмет ревью — PR (`gh pr diff N` или
`gh pr checkout N` для второй CLI).

Реальные замечания — в правки коммитами на ветку фазы, `make verify`, `git push`; PR
обновится сам. (Если захочется автоматизировать: `workflow.code_review_command` в
`.planning/config.json` — ship подаст ему diff на stdin и ждёт JSON с `verdict`;
`REVISE` блокирует ship.)

## 8. Влить

Настройка squash-сообщения репозитория — не в git, применяется один раз командой ниже
(`docs/HOW_TO_DEVELOP.md` — единственная её запись). Без неё squash-коммит наследует
темы коммитов ветки, конкатенированные; так токен попал в `main` дважды (`538d26f`,
`bfc9110`, ни у одного нет прогона). После неё squash-коммит несёт заголовок и тело PR —
тот же curated текст, что `gsd-ship` собирает из артефактов планирования:

```sh
gh api -X PATCH repos/halfb00t/spur \
  -f squash_merge_commit_title=PR_TITLE \
  -f squash_merge_commit_message=PR_BODY
```

Squash-merge PR на GitHub — одна фаза, один коммит в `main`. Затем в основном checkout'е:

```sh
git switch main && git pull --ff-only origin main && git branch -D gsd/phase-NN-<slug>
```

`-D`, а не `-d`: после squash ветка не является предком `main`, и `-d` откажется. Именно
этот обновлённый `main` нужен следующему `gsd-plan-phase` (шаг 2).

Красный CI или незакрытые замечания ревью — не merge. Руками влитая работа, которая
пропустила ревью и verify, — это ровно та дыра, ради закрытия которой всё это стоит.

## Параллельные циклы

Фазы gsd идут по одной: каждая режется от уже влитого `main`. Параллелить есть смысл
работу вне фаз — `gsd-quick`, точечные правки: для них по-прежнему `make worktree.new
SLUG=<slug>` (ветка `agent/<slug>` в `.claude/worktrees/<slug>`) и
`make worktree.land SLUG=<slug> MSG="<commit>"`, который сам проверит чистоту, сделает
squash-merge, ещё раз прогонит `make verify` на слитом результате и только тогда
закоммитит.

Твоя роль смещается с «жду одну вещь» на «держу конвейер заполненным»: пока одна фаза
выполняется, ты обсуждаешь или ревьюишь план следующей. Но оценивай зависимости честно —
два цикла, редактирующие `calc.py`, столкнутся при вливании. Не уверен, что задачи
независимы, — спроси агента до того, как запускать обе.

## Практические правила

- Никогда не одобряй план или результат, который не понимаешь. Спрашивай.
- `make verify` и ревью другим CLI — страховка, а не формальность. Пропуск одного из них
  — это и есть то, как в проект попадает слоп.
- Маленькие фазы лучше больших. Одна за раз.
- Нашёл хорошую идею или срезал угол — зафиксируй файлом в `docs/ideas/` или
  `docs/tech_debt/`, иначе это исчезнет вместе с сессией.
- Если агент утверждает, что стало быстрее или экономнее, требуй цифру и нагрузку.
