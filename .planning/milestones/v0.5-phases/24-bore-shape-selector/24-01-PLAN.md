- **PD-03 -- `deriveSelectors()` beside `applyRelations()` at its three call sites (24-RESEARCH Open Question 1).**
  Pinned tokens 4, 10 and 11 are rewritten to their longer forms and no other existing token changes. Rejected: calling
  it inside `applyRelations()` (no token changes, but it joins two concerns and puts selector code in the relations span
  that `writes_a_value` guards).
- **PD-04 -- a pick's request goes through the form listener (CONTEXT discretion "pick -> request timing"; 24-RESEARCH
  Finding 4).** The select's handler is on `input`. A pick that is not pending performs its writes in the target phase
  and lets the event bubble on: the form listener then runs `applyRelations(); deriveSelectors(); scheduleUpdate();`, the
  same path as a keystroke, so the derive lands on the chosen option (its conditions now hold) and exactly one debounced
  request is sent. A pending pick calls `event.stopPropagation()`, so the listener neither re-derives the select back nor
  schedules a request. This keeps `applyRelations()` and `deriveSelectors()` at exactly three call sites each (L41:
  "called from three places and no others"; D-06), and both hazards Finding 4 measured -- the snap-back and the duplicate
  request -- cannot happen: the first because the writes precede the bubble, the second because the pick calls no
  `update()` of its own. Rejected: `stopPropagation()` on every pick plus a direct `applyRelations(); deriveSelectors();
  update()` (CONTEXT's recommendation): a fourth call site of each, which L42 would have to record against L41's wording,
  for a request 350 ms sooner.
- **PD-05 -- the DOM identity (D-04, D-16 option A).** The row is a `<label class="selector">` holding a `.name` span (the
  selector's `title`), a `.control` span with the `<select>` (no `name`, `id` `selector-<index>`), and a `.reason` span

  inserted before the first `label.field` of the fieldset whose legend is the selector's `group`. It is not `label.field`,
