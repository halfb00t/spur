<objective>
Make every way a build can fail an answer the caller can act on, and give `/api/health`
something to say about the pool without asking it anything.

Plan 02-01 proved the happy path across the process boundary. This plan expands outward
from it to the three ways that path can fail — the kernel refuses the parameters, the
worker dies, the build never finishes — and gives the liveness endpoint the parent-local
pool counters D-13 specifies.

Purpose: D-07's affinity routing is what makes this urgent. One wedged worker is fatal to
1/N of the parameter space until something kills it, and `Executor.shutdown(cancel_futures=True)`
does not: it only cancels futures that have not started. The timeout therefore has to
terminate the process, which is why Plan 02-01 shipped a regression test around the
private `_processes` attribute this depends on.

Output: a per-build timeout that actually stops the build, three distinct failure-mode to
status-code mappings with tests, pool fields on `/api/health`, and `http-api.md` telling
the truth about all of it.
</objective>

  <name>Task 3: Decision — the shape of the pool fields on /api/health (D-13, one-way)</name>
  <decision>The shape of the pool fields on `/api/health`</decision>
  <context>
D-13 adds pool state to `/api/health`: live executors, remaining queue capacity, and
workers replaced since start — all parent-local, O(1) attribute reads, no IPC.

CONTEXT.md rates this **one-way**: `/api/health` is a published response contract. The web
UI reads it, and Phase 4's typed `DerivedDimensions` / OpenAPI work inherits whatever shape
lands here. Removing a field later breaks any client that read it. The *content* was
decided in `/gsd-discuss-phase`; the *shape* was not, and the shape is the part that is
expensive to undo.
  </context>
  <options>
    <option id="option-a">
      <name>Flat keys at the top level</name>
      <pros>Smallest diff; matches the existing two-key response; trivially readable by `curl` and by the healthcheck; what 02-RESEARCH.md sketched.</pros>
      <cons>Every future pool field adds another top-level key to a published contract; the health response's top level becomes a grab bag, and Phase 4 has to type each key individually.</cons>
    </option>
    <option id="option-b">
      <name>One nested `pool` object</name>
      <pros>Adds exactly one top-level key now; every later pool field goes inside it without touching the published top level, which converts a one-way door into a reversible one; Phase 4 types one nested model instead of N scalars.</pros>
      <cons>Marginally more verbose to read by eye; one extra level of indirection for the UI, which currently reads `status` and `version` flat.</cons>
    </option>
    <option id="option-c">
      <name>A separate `/api/pool` endpoint, leaving `/api/health` untouched</name>
      <pros>Leaves the published health contract completely alone; pool state can evolve freely.</pros>
      <cons>A second endpoint to document, test and keep fast; splits liveness across two URLs; goes beyond what D-13 asked for.</cons>
    </option>
  </options>
  <recommendation>
Option B. The reversibility guidance is explicit that the better move, when available, is
to make the decision reversible rather than to gate it — and a nested `pool` object does
exactly that: it is the only option where adding a fourth pool field later is not a second
one-way decision. It also keeps `status` and `version` exactly where the UI and the
container healthcheck already expect them.
  </recommendation>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| HTTP client -> `app.py` | Untrusted query parameters; a deliberately expensive gear is the adversarial input this plan defends against |
| `app.py` -> worker process | A wedged or dead worker is the failure this plan converts into a bounded, reported outcome |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-07 | Denial of Service | `BuildPool.export` / affinity routing | high | mitigate | `SPUR_BUILD_TIMEOUT` bounds every build and Task 1 terminates the worker process rather than abandoning the future; the affected executor is replaced, so a crafted expensive gear costs one build's wall time and not 1/N of the service permanently. | T-02-08 | Denial of Service | admission semaphore (`BUILD_QUEUE`) | high | mitigate | Every failure path releases its slot through `_build_slot`'s `finally`; Task 2 asserts capacity is restored after each of the three failures, so a repeated-timeout attack cannot drain the semaphore into permanent `503`s |
| T-02-09 | Information Disclosure | `/api/health` pool fields | low | accept | Worker count, remaining capacity and a replacement counter are operational facts about a service that ships with no authentication by design (`REQ-no-auth-default`) and binds to `127.0.0.1`. | T-02-10 | Spoofing | error `detail[].type` values | low | accept | The four type values are a closed, documented set the UI switches on; they carry no caller-supplied content beyond the kernel's own `BuildError` message, which is already surfaced today |
