<objective>
Build the measuring instrument before there is anything to measure with it.

Phase 2's two success criteria are both numbers, and CLAUDE.md's standing rule is that a
number this project prints is a number someone cuts metal to. This plan commits a
rerunnable harness — `make bench` — that produces those numbers: the debt file's own two
load scenarios against `/api/health`, and the N = 1, 2, 4 container memory sweep over
L07's own 40-gear corpus.

Purpose: D-16 is explicit that the point is not convenience but falsifiability. A
measurement recorded in a reply dies with the session; a committed harness lets whoever
doubts the claim re-run it. This plan authors the harness only — it is deliberately Wave 1
and runs nothing against the service, because the topology it will measure is being built
in parallel by Plan 02-01. Plan 02-04 runs it.

Output: `bench/` (corpus, latency harness, memory harness, README), three `make` targets,
and `bench/` added to the `typecheck` target so the harness is held to the same
`mypy --strict` standard as `src/`.
</objective>

`bench/corpus.py`: a `corpus() -> list[dict[str, object]]` returning L07's own workload —
40 distinct gears with tooth counts spanning 160 to 199 — as query-parameter dictionaries
ready to hand to an HTTP client. Generate them deterministically from the tooth count so
two runs on two machines drive the identical workload; the module docstring must say
where the corpus comes from (`docs/plan-2026-09-21.md` F2, the same 40 gears that earned
`mem_limit: 2g`) and why it must not be changed: a different corpus produces a ceiling
that cannot be compared with the one on record, which defeats the point of measuring.

`bench/latency.py`: an argparse CLI (`--base-url`, default `http://127.0.0.1:8000`) with
two scenarios, named on the command line and in `--help`:

- `single` — sample `/api/health` in a tight loop for a settling period to get **idle
  p95**, then start one 200-tooth fine build (`/api/model.stl?teeth=200&quality=fine`) in
  a background thread and keep sampling `/api/health` for the whole time it is in flight
  to get **under-load p95**. This is the scenario that produced the recorded 0.22 s ->
  0.76 s -> 2.00 s progression.
- `concurrent` — the same idle sample, then ten concurrent builds, sampling `/api/health`
  throughout. This is the scenario that repeatedly exceeded 5 s.

Use `httpx` (already a dev dependency) and `concurrent.futures.ThreadPoolExecutor` for the
background load; no new dependency. Compute p95 with one named stdlib call —
`statistics.quantiles(samples, n=20)[-1]` — and say in a comment which method that is and
why hand-rolling a percentile is not acceptable here (the number is the acceptance
criterion; an off-by-one in a hand-rolled percentile is exactly the plausible-but-wrong
number L08 forbids). Refuse to print a p95 computed from fewer than 20 samples: report a
warning naming the sample count instead, and exit non-zero. Every reported p95 carries its
sample size.

Emit a markdown fragment on stdout containing: the machine facts (CPU count,
`platform.machine()`, total RAM), the scenario name, idle p95 with its sample count,
under-load p95 with its sample count, the ratio, and the slowest single build observed
(Plan 02-04 sets `SPUR_BUILD_TIMEOUT` above that figure, so the harness has to report it).
Include the recorded baseline verbatim beside the new numbers, labelled as coming from a
different machine, so nobody reads a cross-machine absolute as a target — the acceptance
criterion is the ratio, not the seconds (D-17, RESEARCH.md Pitfall 4).

Everything in `bench/` must pass the project's own gate: `ruff check .` with this repo's
rule set (`ERA` forbids commented-out code, `TRY` bans exception antipatterns, `ARG` bans
unused arguments), `mypy --strict`, and the unfinished-work scan — so no `TODO`, `FIXME`,
`XXX`, `HACK` or `NotImplementedError` anywhere in the file.

`bench/memory.py`: an argparse CLI that drives `docker compose` itself, because
`mem_limit` is a container setting and must be measured under the container's own
accounting (D-17), on Linux/glibc where `malloc_trim(0)` actually does something.

Two modes:

- `sweep` — for each N in 1, 2, 4: bring the service up with `SPUR_BUILD_WORKERS`
  overridden to N and `SPUR_WORKERS` at 1, wait for the container to report healthy (reuse
  the polling shape the `up` target already uses), drive the full 40-gear corpus through
  `/api/model.stl?quality=fine`, poll container memory throughout, and record the **peak**
  for that N along with the request count, the failure count and the elapsed time. Tear
  down between values of N so each row is a cold start, not a carry-over. Emit a markdown
  table with one row per N.
- `confirm` — take a candidate limit as an argument, bring the service up with that
  `mem_limit` and the shipping default worker count, run the same 40-gear corpus, and
  report the failure count. Zero failures is the bar the current `2g` cleared and `1g`
  did not; the mode exists so the chosen number is confirmed rather than asserted (D-18).

Record which memory figure is being read and from where (the `docker stats` field, or the
cgroup peak file) in both the output and a comment — a number whose provenance is not
stated is not a measurement. Record the same machine facts the latency harness records,
plus the image platform, since an emulated `linux/amd64` image on Apple silicon does not
produce a comparable number.

If a value of N produces no samples at all — the container never came up, the corpus never
ran — write a warning naming what failed and leave that row's peak empty. Never write a
plausible figure into a row that was not measured (L08). Exit non-zero when any row is
incomplete, so a partial sweep cannot be mistaken for a finished one.

`bench/README.md`: half a page. What each harness measures, which environment each half
must run in and why (host for latency so the numbers are like-for-like with the recorded
baseline; container for memory because that is what `mem_limit` governs), how to run them,
and the one rule that outranks convenience — the corpus does not change, because a
different workload produces a ceiling that cannot be compared with the one on record.
  </action>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| harness -> running service | The harness is a client of the same public HTTP surface any user has; it crosses no new boundary |
| harness -> Docker daemon | `bench/memory.py` issues `docker compose` commands on the developer's machine |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-04 | Denial of Service | `bench/latency.py`, `bench/memory.py` | medium | accept | The harness deliberately saturates a service — that is its job. It is not in `make verify`, not in CI, and its targets are documented as needing a running service and minutes. The `503` + `Retry-After` path it will trip is the behaviour under test, not a fault |
| T-02-05 | Tampering | `bench/memory.py` -> `docker compose` | low | mitigate | The harness composes `docker compose` argument lists from fixed literals and integers it generated itself (N, and a limit string it validates); no request data and no untrusted string reaches a shell. Build the command as an argument list, never a shell string |
| T-02-06 | Information Disclosure | `bench/` output | low | accept | Recorded output is machine facts (CPU count, architecture, RAM) and timings, committed deliberately as the evidence for the phase's claims. No credentials or request payloads are captured |
| T-02-SC | Tampering | npm/pip/cargo installs | high | mitigate | Not applicable this plan: no package is installed. `httpx` is an existing dev dependency; `argparse`, `statistics`, `platform`, `subprocess` and `concurrent.futures` are stdlib. `pyproject.toml` is not modified. If an install becomes necessary, RESEARCH.md's Package Legitimacy Gate applies first |
</threat_model>
