<objective>
Close the second hole (D-01): nothing stopped a merge of a PR whose checks were red or
absent. PR #2 was merged five minutes after `test (3.10)` failed on run 35993984796.
Two things now stop it. The wall is a ruleset on `main` (D-12, supersedes D-06; applied
and read back in Plan 05-03): GitHub refuses to merge a head without green required
checks or behind `main`. The tool is `make pr.land PR=N`, the sanctioned path through
that wall (D-05): it does what the wall cannot -- refuses a skip token in the squash
text, proves a run appears for the squash commit, does the local follow-up -- and it
keeps its own job and behind checks (flagged assumption 8 says why).

**Task 1, a tracer for the merge path.** The thinnest complete landing, offline and
live. It reads the PR and requires the newest `ci.yml` run on its head to be green on
every required job. It squash-merges with `--match-head-commit` and the exact subject and
body it checked, polls until a run exists for the squash commit, prints its URL, and does
the local follow-up without ever deleting unmerged local work. It ships with the Makefile
target and the required-jobs list next to `ci.yml`.

**Task 2, every refusal.** Test-first, each way a PR can be stale, red, missing or
token-carrying is refused before anything merges: behind or identical to `main`, zero
runs, an unfinished newest run, a missing or non-success job, a skip token in the squash
subject or body. The ordering rule for several runs on one sha is pinned, and so is the
drift test that keeps `required-jobs.txt` equal to what `ci.yml` runs. Then the network
shell is exercised live, read-only, against PR #3.

Purpose: a red, missing or stale run cannot be merged through the sanctioned path, and
every merge through it ends with evidence (a run URL for the new `main` commit) or a
non-zero exit saying there is none.

Output: `scripts/pr_land.py`, `tests/test_pr_land.py`, `.github/workflows/required-jobs.txt`,
the `pr.land` Makefile target, and a comment in `ci.yml` pointing at the list.
</objective>

<flagged_assumptions>
1. **pr.land passes `--subject` and `--body` itself** (planner's choice inside D-05's
   implementation discretion). RESEARCH Pitfall 1 recommended calling
   `gh pr merge --squash` with neither, so that the D-03 repository setting fires, and
   flagged as unverified (A2) whether `gh` honours that setting. Passing the exact
   subject (`{title} (#N)`, the shape GitHub's `PR_TITLE` default produces) and body
   that pr.land just checked for skip tokens does three things. It takes A2 off the merge
   path. It closes a window where the PR body is edited between the check and the merge.
   And it makes the checked text byte-for-byte the text `main` receives. D-03 still
   governs the web button's default. The squash commit is read back once, at this
   phase's own merge (`05-05`'s output section), with a stated failure signal.

2. **The skip-token check on the squash subject and body is an addition to D-05's
   listed steps.** After D-03 that text is `main`'s commit message, and no commit-msg
   hook ever sees it. This phase's own PR body is built by `gsd-ship` from planning
   artifacts that name the tokens literally, so without the check the phase's own merge
   is the likeliest leak. D-05 step 5 would still catch it, but only after a run-less
   commit is already on `main`.

3. **Other additions, each needed by D-05's own steps.** A PR not based on `main` is
   refused, because step 5's evidence only exists for `main` (`ci.yml` runs on pushes to
   `main` only). A head identical to `main` is refused, because there is nothing to
   merge. A dirty working tree is refused before merging, because the folded-in local
   follow-up switches branches.

4. **Check data comes from the REST jobs endpoint, not `gh pr view`'s
   `statusCheckRollup`** (RESEARCH anti-pattern): lower-case `success`, one source of
   truth. Runs are read through `actions/workflows/ci.yml/runs` so a future second
   workflow cannot be mistaken for `ci.yml`.

5. **The list file lives in `.github/workflows/`.** D-05 says "next to `ci.yml`".
   GitHub treats only `.yml`/`.yaml` files in that directory as workflows, so a `.txt`
   is ignored by Actions. That is an assumption about GitHub, confirmed only when the
   first PR run shows no workflow error for it. The drift test parses `ci.yml` with
   regular expressions, not YAML: PyYAML is present only as pre-commit's dependency and
   has no type stubs under mypy `--strict`.

6. **Poll window.** `POLL_ATTEMPTS * POLL_INTERVAL_S` = 60 s, D-05's "~60 s". Planning
   read the recent runs (`gh api …/actions/workflows/ci.yml/runs`): each run was created
   34-51 s after its head commit's own timestamp. That is an upper bound on GitHub's lag,
   because the timestamp precedes the ~42 s pre-commit hook and the push. The real lag
   from merge to run is measured at this phase's own merge and recorded in STATE.md.

7. **`delete_branch_on_merge` read `true` live** (CONTEXT recorded `false`). pr.land
   does not depend on it: it never passes `--delete-branch` (RESEARCH A3 left `gh`'s
   behaviour with that flag unverified) and never touches the remote branch; the
   repository setting alone governs it.

8. **Which pre-merge checks stay under D-12's ruleset: all of them** (D-12 allows reducing
   them to what the ruleset cannot enforce; the plan states the choice). The ruleset
   duplicates two: `behind_by > 0` (its strict up-to-date policy) and the required job
   set (its required status checks). pr.land keeps both, for three reasons.
   (a) Step 5 waits for the squash commit's run to *appear*, not to finish, because the
   merged tree is the checked tree; pr.land makes that claim, so it checks it itself
   instead of resting it on a server setting outside git that it does not read and that
   one `gh api` call removes (D-12's own reversibility). (b) `required-jobs.txt` is held
   equal to `ci.yml` by a test; the ruleset's copy is not in git, so if the two ever
   differ, pr.land's is the one under test. (c) pr.land refuses before the merge with the
   job name, its conclusion or the behind count and what to do; `gh pr merge` against the
   ruleset fails with GitHub's generic policy message. The cost is one compare read and
   the tests already listed. The checks the ruleset cannot make at all, which only pr.land
   makes: the PR is open and based on `main` (a PR to another base is outside the

- `pr_refusals(pr)`: a refusal when `state != "OPEN"` (name the state) and when

- `head_refusals(run, jobs, required)` for this task: no run -- refused, naming the sha

  pins every refusal.)

  `newest_run`, fetch its jobs, return `head_refusals(...)`.
- `land(...)`, in order. Every refusal line starts `pr.land:`, says what is wrong and
  then what to do; a refusal before the merge ends with one line containing
  `nothing was merged`.
  1. Read and parse the PR. Stop on `pr_refusals`.
  2. Refuse a dirty tree.
  3. Run `check_head` on the head sha; stop on refusals.
  4. Merge with the argv above, subject `squash_subject(pr)` and body `pr.body`.
     Non-zero: print gh's stderr and "check `gh pr view {n}` before retrying"; return 1.
  5. Read the squash sha. Poll the runs query for that sha up to `attempts` times,
     calling `sleep(interval_s)` between attempts. On the first non-empty result, print
     the newest run's `html_url`.
  6. Local follow-up: `git switch main`, then `git pull --ff-only origin main` (either
     failing is reported, and the exit is non-zero); then `git branch -D` only when
     `rev-parse` finds the branch and its sha equals the merged head sha. A differing
     tip is kept, with a message naming both shas; an absent branch is skipped quietly.

     `pr.land: PR #{n} IS merged as {squash sha}, but no ci.yml run appeared within
     {attempts*interval_s:.0f} s -- a skip token reached main (L22)` (or the step 6
     failure) and return 1.

  `SystemExit(main())`.
