<hard_fact_1>
CPython 3.12.13 (`.venv/bin/python -V`), `concurrent/futures/process.py`:
`_ExecutorManagerThread._terminate_broken` sets one `BrokenProcessPool` on **every**
entry of `pending_work_items` when a worker is found dead. `flag_executor_shutting_down`
cancels pending items **only** when `_cancel_pending_futures` is set — i.e. only when
`shutdown(cancel_futures=True)` was used. In `run()`, after a shutdown flag is seen the
thread returns early only `if not self.pending_work_items`; with an uncancelled sibling
still pending it loops back into `wait_result_broken_or_wakeup`, where the terminated
worker's sentinel is ready, `is_broken` is true, and `terminate_broken` fires.

So: **with** `cancel_futures=True` the queued sibling's future is cancelled and awaiting
it raises `asyncio.CancelledError` — a `BaseException` that `_run_with_timeout`'s two
handlers, `model()`'s three `except` clauses and Starlette's `ServerErrorMiddleware`
(`except Exception`) all miss. **Without** it, the same sibling is failed with
`BrokenProcessPool`, which `_run_with_timeout` already catches and `app.py` already maps
to `503 pool_broken`. This is the mechanism; Task 1's test is what proves it here.
</hard_fact_1>
