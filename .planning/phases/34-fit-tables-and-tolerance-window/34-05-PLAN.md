<objective>
Make D-04's startup policy real at every composition root and make the tables reach the build workers unchanged. A file
someone meant to load and that cannot be loaded stops the CLI and the server with the reason, instead of quietly printing
nulls (D-04); the parent's one loaded object is what every build worker and every replaced worker uses (D-13, research
Pattern 3), so the maximum-material solid 34-07 builds in a worker is the one the info response describes.

Planner choices (Claude's Discretion, CONTEXT: where the loader lives and how the tables reach `derive_shaft`):
- One call site in the CLI, in `main()` after argument parsing, for every subcommand: CONTEXT says "the server and the
  CLI refuse to start", and one line is simpler than three. Research A5 suggested sparing the gear commands; with the
  variable unset (everyone's default) the gear is untouched, and an operator who set a broken file is told so whatever
  they run. `--help` and `--version` still answer (argparse exits before the call). Recorded for L50 (34-17).
- `cmd_serve` needs no call of its own: `main()` refuses before `cmd_serve` imports uvicorn, so the refusal does not
  depend on how uvicorn's multi-worker supervisor treats a lifespan failure (research A4, unverified).
- `app.lifespan` reads the tables too, as defence in depth for a direct `uvicorn spur.app:app` start (the browser
  test's server and any deployment that skips `spur serve`).

Purpose: a broken file is loud at startup; a loaded file is the same file in every process that builds.
Output: three source edits, ~9 tests, three doc edits.
</objective>
