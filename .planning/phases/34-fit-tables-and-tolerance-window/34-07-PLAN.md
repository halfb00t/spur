<objective>
Make the solid follow the tables (REQ-solid-max-material, criterion 4): with the tables loaded and the fit listed, the shaft
is built at the maximum effective tooth thickness s_vmax = s1 + A_s and that thickness is read back from the solid; without
them it is today's nominal solid, which the warning already says (34-04). Prove the build worker builds the same part
from the parent's tables (34-05's hand-off), and prove in a real browser that the five rows reach the page through the
schema-carried list with no page code (criterion 3).

Planner choices:
- The thickness reaches `_outline` as a shift, research Pattern 5's second option: no `din5480.py` change, and
  tests/test_din5480_anchors.py already uses the same inversion for the oracle.
- The read-back is a test, not an in-build guard: `_guard_volume` brackets the volume with the face's own area, so it
  cannot see a thickness (research Pattern 5).
- The browser proof is one step with its own server, started only for that step, because the shared server strips every
  `SPUR_*` variable and its rows must stay the no-table 42 (research Pitfall 12).

Purpose: the part a user downloads is the part the numbers describe, in every process that builds it.
Output: a three-line change in `build_shaft`, kernel and pool tests, one browser step.
</objective>

<assumption_delta_decision>
noun: tooth thickness (nominal_thickness, and the max-material thickness the solid carries)
decision: add-alongside
rationale: `nominal_thickness` stays a printed row and the thickness of every off-table solid; s_vmax is added beside it from the tables and read by the solid only when printed, and `fit` stays the user's existing field, so no derived value is promoted to a parameter (the detector's "chosen fit" names that existing field).
</assumption_delta_decision>
