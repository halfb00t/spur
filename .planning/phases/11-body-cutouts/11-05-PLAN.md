## Flagged Assumptions

- **A1 (four DIMS rows, not five).** D-20 and the code context speak of `DIMS` rows for the five fields.
  `renderInfo` appends " mm" to every row, so a `hex_cell_count` row would print "18 mm". The count rides
  in the size row's label instead, `span_teeth`'s precedent; the API and CLI carry both fields as usual.
- **A2 (a hex_cell that rounds to 0 is refused).** No decision names it. The applied size is rounded to
  3 dp like every cut value, a request under 0.0005 mm rounds to a zero-size cell, and a zero-size cell is
  not a honeycomb: D-14's reasoning (the link asked for a honeycomb that cannot exist) with the true cause
  in the sentence, as 10-REVIEW.md CR-01 requires.
- **A3 (walls exact on the cut polygons).** CONTEXT's discretion says "the nearest cut cell's corner, from
  the lattice". The nearest point of a hexagon to the axis is a flat for the cells facing the axis (the
  default gear's six inner cells: 6.5 mm on the flat against 6.268 mm at the circumradius), so the plan
  computes the exact point-to-edge distance; the corner reach would under-report the wall by 0.232 mm
  there, a plausible number that is not the part (L08).
