<objective>
Produce the numbers, then set the knobs from them — in that order, never the other way
round.

Everything before this plan built a topology and an instrument. This plan runs the
instrument and lets the results decide four values that are currently placeholders or
inherited: `SPUR_BUILD_TIMEOUT`'s default, `compose.yaml`'s `mem_limit`,
`SPUR_BUILD_WORKERS`' shipping default, and whether `max_tasks_per_child` is on.

Purpose: `REQ-measured-memory-ceiling` exists as a requirement in its own right precisely
because this is the step most likely to be skipped. L07's numbers assumed caches bounded
per process; N workers multiply that, and an estimated replacement ceiling would be exactly
the plausible-but-unverified number L08 forbids. The same applies to the latency claim: the
acceptance bar is a *ratio* measured on one machine, not a match against seconds recorded
on another.

Output: `bench/RESULTS.md` as the committed, re-runnable evidence, and four knobs whose
comments carry the measurement that set them.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| harness -> running service / Docker daemon | The measurement runs are a client of the public HTTP surface and of the local Docker daemon; no new production boundary is introduced |
| `compose.yaml` -> container runtime | `mem_limit` is the backstop behind the in-code cache bounds; this plan sets its value |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-11 | Denial of Service | `compose.yaml` `mem_limit` | high | mitigate | A limit set too low is a self-inflicted outage — `1g` failed ~5% of requests under this same corpus. Task 2 confirms the chosen value by re-running all 40 gears at it and requiring zero failures, and records every failing attempt, so the number is earned rather than asserted |
| T-02-12 | Denial of Service | `SPUR_BUILD_TIMEOUT` default | medium | mitigate | A default below the worst legitimate build turns valid requests into `503`s. Task 1 sets it above the slowest build actually observed, with a margin for slower hardware, and records the observation it is derived from |
| T-02-13 | Information Disclosure | `bench/RESULTS.md` | low | accept | The committed record holds machine facts and timings only — CPU count, architecture, RAM, durations, byte counts. It is committed deliberately: the evidence is the point (D-16). No credentials, hostnames beyond localhost, or request payloads are captured |
| T-02-14 | Repudiation | measurement provenance | medium | mitigate | A number without its machine is unfalsifiable. Every section of `bench/RESULTS.md` is anchored to a `## Machine` block, the memory figure names its source, and both tasks carry a human check that the machine was quiet — so a later reader can tell what the number does and does not prove |
| T-02-SC | Tampering | npm/pip/cargo installs | high | mitigate | Not applicable this plan: no package is installed and `requirements.txt` is not regenerated. `docker compose` pulls no new image beyond this project's own build. If an install becomes necessary, RESEARCH.md's Package Legitimacy Gate applies first |
</threat_model>
